# CallBackIQ scale query update — September 15, 2026

Baseline API: `2ab8b54fa2ebe72b4d0c45a1165e1fde6280ee83`.
Baseline frontend: `59e96c0ae954d347f8bfcdbafe5ca335b9223ced`.

This is an implementation update, not a capacity certificate. No production database, provider account, deployment or GitHub branch was changed while preparing it.

## Changes

- Customer recovery detail returns at most 50 records per section by default (hard maximum 100), plus independent continuation metadata. `GET /api/customers/:leadId/recovery-detail?section=messages&cursor=...&limit=50` walks older history. Supported sections: conversations, messages, calls, appointments, voiceSessions, interventions, intelligence, conversionEvents. Requests without a section retain the existing envelope and add `pagination`. History sorts by createdAt and ID descending; message pages display chronologically. The current conversation, current appointment, unresolved intervention and latest intelligence are selected independently of history pages.
- Recovery reads no longer call lifecycle persistence or update timestamps. Lifecycle and revenue summaries aggregate all linked history, including older completed appointments; they do not derive totals from the visible page. Existing lifecycle persistence/backfill APIs remain available. Canonical display state comes from authoritative records, rather than an asynchronously maintained copy.
- Related histories use indexed lead queries plus a disjoint conversation-linked branch. Legacy records without a lead remain reachable. Both sides enforce tenant scope. No tenant-wide conversation-ID array is transferred to Node.
- Owner opportunities use stable updatedAt/ID cursors, bounded per-lead existence/latest-record joins, and separate cached summary queries. No tenant-wide `distinct()` arrays or page/count `$facet` are used. The Inbox sends the returned cursor, preserves summary counts on continuation, deduplicates records, and rejects late responses after filters change. Existing per-page action/urgency ordering is preserved. Offset clients remain supported through offset 1000; deeper requests receive 400 with a cursor instruction. No infinite or silently truncated offset fallback exists.
- Owner counts are computed from live authoritative collections, cached for 10 seconds and eligible for stale responses up to 30 seconds; `summaryObservedAt` identifies their age. This deliberately avoids introducing an unverified write-hook projection across all SMS, voice, appointment and staff paths. Counts still require work proportional to matching tenant data on refresh. Cursor views that filter related state still perform indexed existence checks until enough matches are found. They have execution deadlines; they are not constant-time queries.
- Existing contains-search behavior is retained, including joined conversation search. Input length and Mongo execution time are bounded. Expensive reads return a retryable 503 with Retry-After instead of running indefinitely. This is not a claim that ordinary B-tree indexes accelerate arbitrary substring search. Use the provided explain probe and no-match load cases to decide whether a deployment needs a dedicated search index.
- Shared Redis cache-refresh ownership combines refreshes across processes, rechecks published data after acquisition, and publishes only while its token is still current. Cold waiters have a finite wait; stale readers use available data. Lost owners cannot overwrite newer results. Redis failure falls back to a bounded number of local database loaders. Freshness is slightly staggered. This implementation targets the existing single-primary/Sentinel Redis client, not Redis Cluster.
- SMS workers share expiring, renewed per-business slots (default five across the fleet), in addition to existing per-conversation and job leases. Saturated tenants are deferred without consuming retry budget. Within a drain, claims prefer businesses not yet served. All lanes settle before the worker clears its running flag. This prevents a failed lane from accidentally allowing overlapping drains. Existing final-attempt reconciliation, uncertain-delivery handling and provider idempotency remain in place.
- Runtime snapshots/logging include sampled SMS processing p50/p95/p99 and tenant deferrals. Queue age remains available from authenticated scale-health. Sizing uses measured job service time, not HTTP webhook acknowledgment latency.
- The deployment generator accepts measured SMS sizing inputs and rejects undersized declared SMS replicas. Optional API/SMS autoscaling budgets Mongo pools against maximum replica counts plus rollout allowance. Voice replicas stay explicit because active WebSocket draining needs separate operational acceptance.
- Mixed-load certification now requires opportunity lists and continuation, customer detail and older messages, matching and nonmatching lead/call/conversation search. Response bounds, expected customer identity, tenant ownership and pagination overlap are checked. Existing voice and SMS outcome gates remain required. The certificate verifier rejects missing expensive-route evidence and requires noisy-tenant, cold-cache, query-plan and sizing observations.

## Install and verify

The downloadable installer checks every changed file against its exact prior SHA-256, permits already-applied files, refuses conflicts, and backs up changes. It never edits `.env`, runs a migration, purchases a number, sends a message or pushes Git. Apply the API and frontend together.

Run `bash verify-local.sh` from the extracted update folder. It runs the new unit and persistence regressions, existing scale release/fleet gates, API build, frontend suite and frontend build. It stops on failure. On macOS it prevents idle sleep while verification runs. It does not close the terminal.

Before promoting a release, run the repository's full `npm run release:certify:ci` on the API as well. Do not weaken coverage or persistence gates to obtain a pass. The package adds the new regression suites to API CI; it does not change CI permissions or assume the previously failed remote jobs were code failures.

## Required staging rollout

1. Apply and review the source changes; pass local and CI gates for the exact API/UI pair.
2. Back up the target database. With its `MONGO_URL` selected explicitly, run `npm run migrate:required-indexes -- --apply`, then `npm run migrate:required-indexes`. The migration is additive; it never drops old indexes. Review additional write/index cost under the acceptance workload.
3. Configure shared Redis and the existing deployment namespace. Defaults added here: `OWNER_QUERY_MAX_TIME_MS=3000` (hard maximum 5000), `SCALE_CACHE_MAX_LOADERS=8`, `SMS_CLAIM_MAX_TIME_MS=2000`, `SMS_TENANT_MAX_CONCURRENCY=5`. Raise limits only from measurements; raising a timeout does not remove a scan.
4. Run the read-only probe with `SCALE_PROBE_BUSINESS_ID`, `SCALE_PROBE_LEAD_ID`, `RELEASE_SHA` and optional `SCALE_PROBE_SEARCH`: `npm run probe:scale-queries`. The JSON report contains redacted plan stages, examined document/key counts, time and dataset counts. It does not write data or include customer payloads. These are representative query-plan probes; the mixed HTTP workload tests the actual endpoints.
5. Measure processing time with normal and slow-provider loads. Example planning inputs: `SCALE_SMS_JOBS_PER_SECOND=200 SCALE_SMS_PROCESSING_P95_MS=2000 npm run plan:sms-capacity` recommends 26 replicas at 25 lanes and 65% target utilization including one spare. This is planning arithmetic, not a measured benchmark. Configure `SCALE_REPLICAS_WORKER_SMS` and rerender only when infrastructure, Mongo and provider budgets support it.
6. Optional autoscaling: set `SCALE_AUTOSCALING_ENABLED=true`, `SCALE_MAX_REPLICAS_API` and `SCALE_MAX_REPLICAS_WORKER_SMS`. Install the CPU metrics server and an external-metrics adapter exporting `callbackiq_sms_oldest_job_age_seconds` with the `deployment` label equal to the scale namespace. It must collect authenticated scale-health's `smsOldestAgeMs / 1000`, enforce freshness, and report missing/stale data as unavailable (never zero). Verify it before setting `SCALE_SMS_METRICS_ADAPTER_READY=true`. The generator creates HPA resources only with that explicit declaration. It does not install or certify an adapter. Review provider quotas at the maximum worker count, not just the minimum.
7. Populate dedicated staging fixtures for the mixed workload: every tenant manifest entry now needs `probeLeadId` and `probeSearch` (typically that customer's phone), at least 1000 leads unless a larger `minimumLeadCount` is specified, 21+ messages for the probe customer, and matching call/conversation history. Put calls/appointments across older dates and also test a few tenants with much larger histories. Existing manifest fields businessId, token, to, from remain required. The runner neither seeds nor buys numbers. Provider costs apply to the existing live SMS/voice workload; use authorized staging destinations.
8. Run mixed cohorts and the required soak using existing commands. Read-path gates default to p95 <=1500ms / p99 <=3000ms for each route, including no-match searches. Existing dashboard/voice/SMS thresholds are unchanged. If representative searches or counts exceed their budget, the release has not passed; provision a dedicated search/read model based on evidence instead of claiming a timeout is successful capacity.
9. Exercise two+ replicas with cold cache, unavailable Redis, paused/terminated SMS workers, one noisy business, Mongo failover, provider 429/timeouts and replay. Verify no duplicate business effects, no wrong-tenant records, and bounded queue age. Check graceful shutdown independently from abrupt process loss.

## Rollback

Use `node install.mjs --rollback /absolute/path/to/the/reported/backup` only while changed files still match this update. The installer refuses to overwrite subsequent edits. Restore both source sets together. Retain additive indexes and existing job/delivery identities; do not delete them to force retries. Remove any newly applied HPA resources separately through the deployment workflow if reverting autoscaling. Source rollback does not undo deployments or external business effects.
